# A4.4 — Security Architecture Remediation Proposal

**DESIGN ONLY — NOT IMPLEMENTED, NOT AUTHORIZED FOR EXECUTION.** This proposal addresses the blockers from the independent A4.3 adversarial review. It does not connect to Neon, execute SQL, run migrations, configure providers, deploy services, or change any database, credential, role, grant, financial rule, oracle-assurance rule, or freshness limit.

## 1. Decision summary

The required threat model cannot be met by a local-only binding file and local attempt ledger.

The proposed architecture requires two independently controlled authorities:

1. **Metadata signing authority** — signs a canonical target manifest with a hardware-backed or offline Ed25519 key. The corresponding public key is pinned in the reviewed release, not supplied with the manifest.
2. **Append-only attempt authority** — atomically reserves one migration attempt per signed manifest and retains a remotely signed, non-deletable-by-the-migration-principal state transition history.

Local files can be caches and diagnostic evidence only. They are not the authority for metadata authenticity or one-use migration permission. Windows ACLs, exclusive file creation, and handle checks protect against mistakes and less-privileged users; they do **not** protect against a machine administrator, `SYSTEM`, the same service identity, kernel compromise, or host loss.

No migration can start unless both independent authorities are reachable and return valid signed receipts. Once the authority records `MIGRATION_STARTED`, no automatic retry is permitted under any outcome.

### 1.1 Confirmed administrator-compromise decision

The qualification Windows host is explicitly **untrusted**. The threat model includes an attacker with administrator-level access who can read/replace local files and executables, change launch arguments/environment/ACLs/ownership/trust stores, inspect or inject into processes, delete local receipts/logs, terminate work and manipulate local time.

Consequently, the Windows machine cannot be the authoritative migration executor and cannot receive a reusable direct operator credential. A local administrator could bypass every local signature check by replacing the verifier and invoke PostgreSQL directly with any credential available to that host. No arrangement of NTFS ACLs, local public-key pins, process isolation or local receipts solves that problem.

The selected architecture therefore moves final signature verification, one-use reservation, authorization of `MIGRATION_STARTED`, signed-receipt verification, direct credential custody and execution of the exact migration runner to an **independently administered execution environment** outside the compromised Windows administrator's control. The Windows host may request, display and cache signed artifacts, but it cannot authorize, transition, reset, delete or execute an attempt.

## 2. Threat model

### 2.1 Protected assets

- Exact Neon project, branch, parent branch, endpoint and database identity.
- Direct/unpooled endpoint selection and verified TLS/channel binding.
- Approved PostgreSQL 17 migration SQL and SHA-256 checksums.
- Approved `watchdog_pg` catalog fingerprint and namespace `watchdog_free`.
- Proof that the target is disposable and not production.
- One-use migration authorization and attempt history.
- Migration result classification: committed, absent, partial/mismatched, or unknown.
- Existing historical seals, SQLite databases, financial calculations, thresholds, oracle `UNVERIFIED`, freshness `UNKNOWN`, 600-second freshness limit, and `actionable:false`.

### 2.2 Adversaries and failures considered

- Incorrect operator input or wrong branch selection.
- Malicious/replaced metadata file.
- Same-process dependency injection, custom Node loader, or untrusted imported module.
- Path traversal, symlink, junction, hardlink, alternate data stream, parent-directory replacement, and check/open races.
- Caller-controlled environment variables and working directory.
- Duplicate invocation, process crash, host loss, power loss, and deleted local state.
- Connection/query/cleanup timeout with late completion.
- Database changes between preflight and migration.
- Lost COMMIT acknowledgment.
- Compromised migration host, including a local administrator, after authorization material has arrived.
- Replacement of the local verifier/public key, executable, environment, trust store and logs by that administrator.
- Theft of any credential delivered to the Windows host; therefore no privileged migration credential may be delivered there.

### 2.3 Explicit limits

- A local administrator or equally privileged attacker can replace binaries, read process memory, change ACLs, intercept local IPC, delete local files, alter clocks, and launch a modified process. Local controls cannot defeat that actor.
- A pinned public key detects forged metadata but does not stop an administrator from running a different binary that omits verification. Release identity and independent attempt receipts are therefore required together.
- Verification performed only on the compromised Windows host is advisory. Authoritative signature and receipt verification must occur again on the independent runner using its own pinned release/key material.
- A direct database credential present on the Windows host would let the administrator bypass the attempt authority. The independent runner must obtain and use that credential without releasing it to Windows.
- Neon itself remains trusted to return correct authenticated Management API metadata and PostgreSQL endpoint behavior. Provider compromise is outside this design.
- Cryptographic algorithm/key compromise is outside normal operation and triggers key revocation plus a new release review.

## 3. Trust boundaries and principals

| Principal | Authority | Explicitly denied |
| --- | --- | --- |
| Read-only metadata collector | Read Neon project/branch/database/endpoint metadata only | SQL, connection strings, writes, migrations, branch/endpoint changes |
| Metadata signer | Validate collected metadata and sign canonical manifest | Neon database password, migration connection, migration execution |
| Untrusted Windows coordinator | Submit a signed-manifest reference/request and display signed results | Signing keys, attempt-authority mutation credentials, direct DB credential, authoritative state transition, migration execution |
| Independent migration orchestrator/runner | Reverify signature/release, reserve attempt, run bounded preflight and exact migration runner using an ephemeral direct credential | Metadata signing, receipt deletion/reset, automatic retry, production branch access |
| Attempt authority | Atomic reserve and append state transitions; return signed receipts | Neon/database credentials, migration execution, changing signed metadata |
| Independent direct-credential broker | Release one branch-specific, short-lived direct capability only to the independent runner after authorization | Release to Windows, metadata signing, production URLs, long-lived project storage |
| Unknown-outcome inspector | Read-only target inspection and signed resolution proposal | Migration, repair, retry, role/grant changes |
| Human approver | Approve manifest, release, reservation, and final disposition | Secret disclosure into chat/source/logs |

The metadata signer, attempt authority, credential broker and independent runner must be administered outside the Windows administrator's security domain. The Windows administrator receives no signing key, authority transition/delete/reset credential, direct operator connection or runner-management credential. Compromise of Windows must not permit either `reserve` or `MIGRATION_STARTED` without independently valid authorization.

## 4. Signed metadata manifest

### 4.1 Format

Use a versioned canonical JSON payload encoded with RFC 8785 JSON Canonicalization Scheme (JCS), prefixed by a domain-separation string before signing:

```text
LIQUIDATION_WATCHDOG_A4_NEON_TARGET_V1\n<JCS manifest bytes>
```

Required fields:

```text
kind = LIQUIDATION_WATCHDOG_A4_NEON_TARGET
schemaVersion = 1
manifestId = random 128-bit or stronger identifier
sequence = signer-controlled monotonically increasing integer
issuedAt = canonical UTC
expiresAt = canonical UTC (short acceptance window)
projectId
projectName = liquidation-watchdog-pg17
branchId
branchName = a4-migration-test
parentBranchId
parentBranchName = production
endpointId
endpointType = direct
endpointHostnameSha256
endpointPort = 5432
databaseName = neondb
postgresMajor = 17
schemaName = watchdog_pg
namespace = watchdog_free
migrationChecksums = [approved v1, approved v2]
catalogFingerprint = approved production fingerprint
releaseManifestSha256
gitIndexSha256
purpose = SCHEMA_ONLY_DISPOSABLE_QUALIFICATION
```

The endpoint hostname may remain absent from the manifest; its lowercase ASCII SHA-256 is sufficient when the direct URL is injected privately and rehashed in memory. The endpoint ID and branch relationship remain explicit.

### 4.2 Signature envelope

```text
algorithm = Ed25519
keyId
manifest = canonical field object
signature = base64url Ed25519 signature
```

The envelope must not contain its own trusted public key. The verifier rejects unknown algorithms, keys, fields, duplicate JSON keys, non-canonical timestamps, altered ordering/encoding, or signature malleability.

### 4.3 Key control

- Generate the signing key on an offline operator workstation or hardware-backed key service controlled by the security/release approver, not the migration host.
- The signer obtains metadata through Neon OAuth restricted to `readonly=true` and metadata categories only.
- The signer independently checks project/branch/parent/endpoint relationships and produces the signature only after human review.
- The untrusted Windows host may receive the signed manifest and public key for advisory display, but the independent runner obtains them from an independently authenticated source and verifies them again. Local copies are never authoritative.
- Pin the Ed25519 public key and `keyId` in a separately reviewed release input protected by the historical release/seal process.
- Key rotation requires a new reviewed release or a dual-signature transition accepted by both old and new pinned keys. Revocation blocks unused manifests and requires the attempt authority to reject the revoked `keyId`.

### 4.4 Expiry and replay

- Enforce `issuedAt <= trusted wall time + small skew` and `expiresAt` within a short policy window (proposed 15 minutes).
- Enforce a maximum manifest lifetime, not just current age.
- Compare approval expiry using monotonic process time after initial wall-time validation.
- The attempt authority atomically rejects a second reservation for the same `(manifestId, sequence, releaseManifestSha256)`.
- A higher sequence does not automatically supersede a started attempt; human resolution is mandatory.
- Unsigned, expired, future, replayed, wrong-purpose, wrong-release, wrong-project, wrong-branch, wrong-parent, pooled, wrong-port, wrong-major, wrong-database, wrong-schema, wrong-checksum, or wrong-catalog manifests fail before any connection.

## 5. Independent one-use attempt authority

### 5.1 Local ledger decision

A protected local ledger is **not adequate** for the required threat model because:

- An administrator/same identity can delete or replace it.
- A caller can switch to a new path.
- Host loss destroys it.
- NTFS flush/ACL behavior does not create an independent receipt.
- It cannot coordinate attempts from another host after an uncertain outcome.

A local receipt can remain as a redundant cache, but absence or mismatch never authorizes retry.

### 5.2 Required remote authority properties

Use a separately administered append-only/CAS service or equivalent WORM-backed authority. Provider selection is unresolved; no service is authorized by this document.

The authority's reserve/append/signing credentials must not exist on the Windows host. A Windows-originated request is untrusted input; the authority accepts it only when the signed manifest, human authorization policy, release identity and expected state all verify independently. Read-only public receipt retrieval may be exposed if it cannot disclose secrets or mutate state.

Required API semantics:

1. `reserve(manifestId, sequence, releaseHash, manifestSignatureHash)`
   - Atomic create-if-absent.
   - Returns a signed reservation receipt with `attemptId`, authority sequence and time.
   - Duplicate reservation returns the existing receipt/status, never a fresh attempt.
2. `append(attemptId, expectedPreviousState, nextState, eventHash)`
   - Compare-and-append only.
   - Migration principal can append but cannot delete, reset, overwrite or create a second attempt.
3. `read(attemptId|manifestId)`
   - Returns complete hash-chained history plus authority signature.

State machine:

```text
RESERVED
  -> PREFLIGHT_PASSED
  -> MIGRATION_STARTED
  -> QUALIFIED
  -> OUTCOME_UNKNOWN
  -> INSPECTED_COMMITTED | INSPECTED_ABSENT | INSPECTED_PARTIAL
  -> CLOSED_BY_HUMAN_DECISION
```

No transition from `MIGRATION_STARTED`, `OUTCOME_UNKNOWN`, `INSPECTED_COMMITTED`, or `INSPECTED_PARTIAL` permits automatic migration retry. `INSPECTED_ABSENT` still requires a new signed manifest/sequence and explicit human approval; the old attempt is never reused.

### 5.3 Crash/deletion/host-loss behavior

| Event | Required result |
| --- | --- |
| Crash before `MIGRATION_STARTED` | Existing reservation remains; operator may close it only after proving no migration began. No automatic retry. |
| Crash after `MIGRATION_STARTED` | Authority remains started/unknown and blocks every attempt. Run read-only inspector. |
| Local receipt deleted | Remote authority still blocks replay; deletion is an incident, not permission. |
| Migration host lost | New host reads remote signed receipt; cannot reserve same manifest. |
| Authority unavailable before start | Stop; do not migrate. |
| Authority unavailable after local preflight but before start | Stop; reservation remains. |
| Authority acknowledgment lost during `MIGRATION_STARTED` append | Treat as unknown; query authority by idempotency key. Do not invoke migration until signed started receipt is obtained. |
| Authority lost after migration starts | Treat database outcome as unknown and operation incomplete; no retry. |

The migration call starts only after the orchestrator receives and verifies the signed `MIGRATION_STARTED` receipt.

The authoritative transition is performed by the independently administered orchestrator/authority, not by a Windows process. A locally fabricated `MIGRATION_STARTED` event has no effect.

## 6. Filesystem architecture on Windows (defense in depth only)

Nothing in this section is an independent trust boundary against the confirmed administrator attacker. These measures reduce accidental misuse and attacks by less-privileged identities only. Authoritative manifests, receipts, authorization decisions and migration execution remain remote/independent.

### 6.1 Project/release anchoring

- Derive the source/release root from `import.meta.url` using `fileURLToPath`, then `realpath`, never `process.cwd()`.
- Verify the script/build byte hash against the signed release manifest before reading authorization material.
- Refuse `NODE_OPTIONS`, custom loaders, preload hooks, inspector/debug injection, and unreviewed module-resolution paths in the standalone child.
- Use an immutable packaged/compiled entrypoint rather than importing the safety library into an arbitrary long-lived process.

### 6.2 File access

Prefer transmitting the signed metadata envelope over authenticated IPC from the signer/receipt client into the standalone process, eliminating mutable path lookup. If a file is necessary:

- Use a dedicated private NTFS directory owned by a separate service identity.
- Reject UNC, network shares, device paths, alternate data streams, relative paths and path traversal.
- Open every directory component and final file with Windows no-follow/reparse-point semantics (`CreateFileW` with `FILE_FLAG_OPEN_REPARSE_POINT` where applicable).
- Reject every reparse point/junction, not only the immediate parent.
- Reject hardlinked authorization files (`nNumberOfLinks != 1`).
- Obtain a file handle first; validate volume serial, file ID, final normalized path (`GetFinalPathNameByHandleW`), size and ACL from that handle; read bytes from the same handle.
- Recheck file ID/metadata after read. Never validate by path and reopen by path.
- Use exclusive sharing flags appropriate to prevent replacement during verification/use.
- Keep the handle open until its bytes have been signature-verified and consumed.

Node's ordinary `lstat`/`readFile` path APIs do not provide all required Windows handle/no-follow guarantees. A small reviewed native helper or a restricted authenticated IPC transport is required; adding such a dependency requires its own supply-chain review.

### 6.3 ACL guarantees and limits

Windows ACLs can restrict ordinary users and service identities. They cannot protect against:

- Local administrators taking ownership/changing ACLs.
- `SYSTEM` or kernel-level access.
- The same identity that owns both verifier and authorization files.
- Offline disk modification without independent signature checks.

ACLs are defense in depth only. Manifest signatures and remote attempt receipts remain authoritative.

### 6.4 Local cache durability

If a local cache receipt is retained:

- Create with exclusive create-new semantics.
- Flush file contents and metadata.
- Use write-through semantics where available.
- Flush/close the containing directory handle where the platform supports it.
- Record file ID and remote receipt hash.
- Treat missing cache as an incident and consult the remote authority; never infer permission.

## 7. Process and execution isolation

### 7.1 Windows process role

Any standalone process on the Windows machine is defense in depth only. It may verify/display signatures, submit a request and monitor signed receipts, but its output cannot authorize migration. Replacing or injecting into it must not yield a signer key, attempt transition authority or database credential.

### 7.2 Independently administered runner

Use three short-lived processes on an independently administered runner, each built from an immutable reviewed release:

1. **Metadata verifier/reservation process** — no database credential; verifies signed manifest and reserves attempt.
2. **Read-only preflight process** — receives one direct credential through a private broker, runs fixed read-only queries, closes/destroys its socket, and returns a signed/hashed preflight result to the orchestrator.
3. **Migration process** — receives the manifest, preflight result and signed started receipt; invokes only the existing migration runner and verifier.

The independent parent orchestrator is a sealed executable with no plugin/module/test-injection API. It fetches the immutable release and signed manifest from independently authenticated sources, verifies both, and launches children with an explicit environment allowlist:

```text
PATH/SystemRoot/TEMP values required by runtime
one direct operator connection capability
signed manifest input/handle
signed attempt receipt input/handle
fixed release/namespace identifiers
```

Explicitly omit/refuse:

```text
WATCHDOG_POSTGRES_WRITER_URL
WATCHDOG_POSTGRES_READER_URL
DATABASE_URL
NODE_OPTIONS
NODE_PATH
all notification variables
all Render/Cloudflare credentials
all arbitrary preload/loader/debug variables
```

No untrusted application code runs in the process. No exported function accepts alternate clients, migrations, verifiers, catalogs, environments or paths.

The runner's administration, workload identity and logs must be inaccessible to the Windows administrator. A self-hosted runner qualifies only if it is on a separate host/account controlled by a different administrator; installing it on the same Windows machine does not satisfy the threat model.

## 8. Network cancellation and late-work prevention

### 8.1 Preflight connection/query

On the independent runner, use both server and client enforcement:

- 5-second connection timeout.
- Client-level query timeout.
- Server `statement_timeout`, `lock_timeout` and `idle_in_transaction_session_timeout` set as early as the protocol safely allows.
- Explicit per-operation monotonic outer deadline.
- Track the actual `Client` and active query.

On timeout:

1. Request PostgreSQL query cancellation when a backend/query exists.
2. Destroy the underlying socket/client, not merely abandon `Promise.race`.
3. Terminate the read-only child process after a short cleanup allowance.
4. Parent waits for OS process exit and verifies no child/socket remains before issuing any approval.

Because preflight begins `READ ONLY`, disconnect/server termination aborts its transaction. A late promise cannot invoke migration because the migration process does not exist until the preflight child has exited successfully.

### 8.2 Migration process

Preserve existing bounds and code:

- Existing 1-second lock timeout.
- Existing 5-second statement timeout.
- Existing 10-second transaction bound.
- Existing `synchronous_commit=on`.
- Existing advisory lock and checksum/catalog checks.

An outer supervisor deadline may terminate the child to prevent late JavaScript continuation, but any termination after `MIGRATION_STARTED` is `OUTCOME_UNKNOWN`. Socket destruction can trigger server rollback before COMMIT, but it cannot prove rollback if COMMIT may have been sent. Never retry based only on local timing or process exit.

Cleanup failure after migration start is also unknown and leaves the remote attempt authority blocking further execution.

## 9. Approval lifecycle

An approval is an in-memory, non-serializable capability created only after:

1. Signature and pinned-key verification.
2. Manifest freshness and release binding.
3. Remote attempt reservation receipt verification.
4. Successful read-only preflight on the exact host hash/port/database.
5. Preflight child exit and socket-cleanup confirmation.

Approval fields bind:

- Signed manifest hash/signature/key ID/sequence.
- Project, target branch, parent branch and endpoint IDs.
- Direct hostname hash and port 5432.
- Database `neondb`, PostgreSQL 17, schema absence and advisory-lock absence.
- Release hash, migration checksums, catalog fingerprint and namespace.
- Remote `attemptId` and latest signed receipt hash.
- Preflight result hash and database observation time.
- Monotonic issuance/deadline (`performance.now()`/`hrtime`), not wall-clock expiry.

The orchestrator consumes the approval irreversibly, then obtains a signed remote transition to `MIGRATION_STARTED`. Only after verifying that receipt does it start the migration child. The approval cannot be cloned, exported, persisted or reused.

The receipt signature is verified authoritatively on the independent runner using a public key/release trust root unavailable for replacement by the Windows administrator. Local Windows verification is informational only.

## 10. Preflight-to-migration race

Closing preflight before migration creates an unavoidable interval. The design handles it through layered detection rather than claiming race elimination:

1. Preflight verifies PostgreSQL 17, exact database, absent `watchdog_pg`/lineage, and no migration advisory lock.
2. Orchestrator obtains/records the signed `MIGRATION_STARTED` receipt.
3. Migration child immediately invokes the **unchanged** `applyPostgresMigrations()`.
4. Existing runner obtains `pg_advisory_xact_lock(1672,10001)` inside its transaction.
5. Existing runner validates migration ordering/checksums under that lock.
6. Conflicting objects cause DDL failure; no repair or skip is attempted.
7. Existing final `verifyPostgresSchema()` checks versions, database identity, PostgreSQL 17 and complete catalog fingerprint before COMMIT.
8. Wrapper performs an additional post-commit read-only verification.

No external preflight can make a race impossible without changing the migration runner to share the same transaction/lock. This proposal preserves the runner unchanged: any intervening schema change must therefore produce rollback/failure or an unknown outcome, never acceptance. An error after `MIGRATION_STARTED` cannot be retried automatically.

## 11. Failure and recovery matrix

| Failure | Classification | Required action |
| --- | --- | --- |
| Invalid/unknown signature or key | STOP | Reject before connection; investigate signer/release. |
| Expired/future/replayed manifest | STOP | Obtain a newly signed manifest after review. |
| Metadata/URL host hash, port, branch, DB or major mismatch | STOP | No connection or migration; investigate target selection. |
| Attempt already reserved/started | STOP | Read append-only history; never reserve another automatically. |
| Attempt authority unavailable | STOP | Do not migrate. |
| Preflight connect/query timeout | STOP/UNREACHABLE | Destroy socket/process; verify exit; retain reservation. |
| Preflight schema/lineage/lock conflict | STOP | Preserve result; investigate database actor/state. |
| Local cache missing/deleted | INCIDENT | Consult remote authority; absence grants nothing. |
| Windows administrator replaces verifier/config/key/trust store | UNTRUSTED LOCAL RESULT | Independent authority/runner ignores local result; no reserve/start/credential release. |
| Windows administrator fabricates or replays a signed-receipt-shaped object | STOP | Independent signature, manifest, sequence, state and attempt checks fail. |
| Windows administrator deletes all local state or loses host | INCIDENT | Remote manifest/attempt history remains authoritative; another attempt is still blocked. |
| Crash before signed `MIGRATION_STARTED` receipt | STOP | Resolve reservation with authority/human review. |
| Error/crash/timeout after signed start | OUTCOME_UNKNOWN | Append unknown event; run read-only inspector; no retry. |
| COMMIT acknowledgment lost | OUTCOME_UNKNOWN | Same as above; do not infer rollback. |
| Inspector exact committed | INSPECTED_COMMITTED | Close by human decision; proceed only to later acceptance, never rerun. |
| Inspector fully absent | INSPECTED_ABSENT | Human may authorize a new signed manifest/attempt; old attempt remains closed. |
| Inspector partial/catalog/lease/data mismatch | INSPECTED_PARTIAL | Quarantine branch; no repair/retry. |
| Host loss | INCIDENT/UNKNOWN | Recover remote receipts and signed manifest on reviewed host; inspect before any decision. |
| Remote receipt loss/corruption | STOP | Independent authority recovery; no migration. |

## 12. Adversarial test strategy

### A4.3 finding 1 — metadata independence/authenticity

- Valid signature with pinned key passes.
- Wrong key, unknown key ID, altered byte, reordered/noncanonical object, duplicate JSON key and malformed signature fail.
- Manifest-provided public key is ignored/rejected.
- Stale, future, overlong lifetime and replayed manifest fail.
- Same metadata with attacker-generated key fails.
- Key rotation and revoked-key fixtures.

### Finding 2 — path and TOCTOU

Windows-native tests in disposable directories:

- Symlink/reparse point at file, immediate parent and every ancestor.
- Junction substitution.
- Hardlink alias.
- Alternate data stream.
- UNC/device/relative/traversal/reserved-name paths.
- Wrong working directory (project identity remains unchanged).
- File replacement between validation/read.
- Parent rename/replacement between validation/open.
- Final-path/file-ID change during read.
- Verify handle-based reader consumes the originally validated file only.

### Finding 3 — one-use receipt authority

- Two concurrent reserves: exactly one succeeds, second receives same existing receipt.
- Repeated manifest/sequence rejected after every state.
- Local receipt deletion and path switching do not permit reserve/start.
- Host loss/new host cannot reserve same manifest.
- Lost reserve/start response reconciles by idempotency key.
- Principal cannot delete/reset/overwrite receipts.
- Hash-chain/signature tamper fails.
- Authority outage before/after started state.

### Finding 4/6 — approval and process boundary

- Approval cannot serialize/clone/reuse.
- Monotonic expiry despite wall-clock rollback/forward jump.
- Consume-before-start ordering fault injection at every instruction boundary.
- No migration child starts without signed started receipt.
- Production executable exports no dependency injection/test hooks.
- Custom `NODE_OPTIONS`, loaders, preload modules and filtered environment are refused.
- Replaced Windows executable/config/public key cannot cause remote reservation, `MIGRATION_STARTED`, credential release or migration.
- Windows process memory contains no signer, attempt-authority mutation or direct database credential.

### Finding 5 — actual environment

- Each prohibited variable, including empty string and case variations on Windows.
- Minimal allowlist drops unrelated inherited variables.
- Direct capability exists only in child and is absent from logs/arguments/evidence.
- Direct capability is delivered only to the independent runner, never the Windows host.

### Finding 7/10 — network cancellation/cleanup

Use a local fake TCP/PostgreSQL test server, never Neon:

- DNS/connect blackhole.
- TLS handshake stall.
- Authentication stall.
- Hanging BEGIN.
- Hanging timeout setup.
- Hanging catalog query.
- Query cancel acknowledgment/loss.
- Socket destruction confirmed by server EOF.
- Child termination confirmed; no late event/migration invocation.
- Cleanup/end hang.
- Migration child kill before/during COMMIT produces unknown and blocks retry.

### Finding 8 — inspector completeness

Individually vary every lease field:

- `fence`
- `owner`
- `expires_at`
- `deadline_at`
- `current_execution`
- `high_water_slot`
- lease incarnation

Individually insert one row into each of all 12 application tables and require `PARTIAL_OR_MISMATCHED`:

1. cycles
2. streams
3. fingerprints
4. alerts
5. deliveries
6. delivery_attempts
7. delivery_events
8. provider_limits
9. oracle_assurance
10. worker_runtime
11. operational_events
12. scheduled_executions

Also test missing/extra migration rows, wrong checksums, backend/namespace/UUID mismatch, catalog drift, wrong major/database, partial objects, unreachable network and close failure.

### Finding 9 — import safety

- Import every production module under socket/fs/process spies.
- Assert zero network, environment read, file read/write, timer, child process and migration calls at module initialization.

### Race and runner preservation

- Inject schema object after preflight but before runner; require transactional failure/catalog mismatch.
- Concurrent runner lock contention fails under one-second bound.
- Verify exact approved migration SQL/checksums and production catalog constant before process launch.
- Static/build assertion that only existing `applyPostgresMigrations` and `verifyPostgresSchema` are invoked.
- Attempt to submit requests from a fully compromised Windows fixture; remote test authority rejects absent/invalid independent approval.
- Replace local certificates/trust store/clock/executable/config and prove no remote authority transition occurs.

## 13. Execution sequence

1. On the independent runner, verify reviewed release and pinned signer public key from independently authenticated sources.
2. Collect Neon metadata through read-only project-scoped management access outside the Windows trust domain.
3. Sign canonical metadata on independent signer/HSM after human review.
4. Windows may submit the manifest reference, but the independent runner fetches and verifies signature/release/expiry itself.
5. Independent orchestrator reserves one attempt; it verifies the signed reservation receipt.
6. Independent credential broker releases the direct capability only to the isolated runner preflight child.
7. Cancel/destroy/terminate on any timeout; require confirmed child exit.
8. Validate preflight result and create monotonic, one-use in-memory approval on the independent runner.
9. Consume approval.
10. Independent orchestrator authorizes/appends `MIGRATION_STARTED`; require signed authority acknowledgment.
11. Launch isolated migration child using exact existing runner and verifier.
12. Append `QUALIFIED` only after post-verification; otherwise append `OUTCOME_UNKNOWN`.
13. For unknown outcome, run isolated read-only inspector and append its result.
14. Require human closure; never automatic retry.

## 14. Cost and deployment implications

No provider/component is selected or authorized by this proposal. No paid infrastructure, subscription, payment method or billable operation may be created without explicit approval.

Candidate approaches:

| Candidate | Potential fit | Qualification/cost caveats |
| --- | --- | --- |
| Independently administered self-hosted Linux runner + self-hosted append-only service | Can satisfy separate administrator/control domain without subscription fees if existing hardware is available | Hardware, patching, availability, backup, key custody and operator time are real costs; the host must not be administered by the Windows attacker |
| GitHub-hosted or equivalent ephemeral CI runner with protected environment, OIDC and manual approval | Independent execution host and immutable workflow/release controls may fit; free allowances may cover rare qualification | Requires separate account/repository/environment security review; private-repo minutes/retention limits apply; no paid overage may be enabled without approval |
| Cloudflare Worker/Durable Object as receipt authority only | CAS/serialized remote state may fit Free allowances | Separate account/admin required; retention/export/signing and Free-limit behavior need proof; not proposed as the PostgreSQL migration runner |
| Managed KMS/HSM + WORM/ledger service | Strong key and append-only controls | Commonly paid; prohibited without explicit budget/provider approval |
| Same Windows host, local VM/container/service, local file/SQLite ledger | Low apparent cost | **Rejected**: same administrator can alter/delete/bypass all components |
| Same Neon project/database as attempt authority | Convenient | **Rejected as sole authority**: shares target/provider/failure and administrative domain; cannot independently resolve uncertain target outcomes |

“Self-hosted” satisfies the requirement only when it is physically/logically separate, independently administered and unavailable to the compromised Windows administrator. Running another service, VM, container or account under that administrator on the same machine does not qualify.

Before selection, compare zero-cost allowances, forced paid upgrades/overages, log/receipt retention, CAS semantics, cryptographic signing, administrator separation, disaster recovery and availability. If no free or already-owned independent option meets all controls, A4 remains blocked until the user explicitly approves a paid design or changes the security requirement.

## 15. Remaining risks and unresolved decisions

- Select and approve the metadata signing technology (offline Ed25519 key versus hardware-backed service) and custodians.
- Select an independent append-only receipt authority/provider with CAS, signed receipts, retention and recovery guarantees.
- Define authority availability, retention, export and disaster-recovery targets.
- Decide whether a reviewed Windows native handle/no-follow helper is acceptable or whether authenticated IPC removes file inputs.
- Define the standalone packaging/signing format and Windows service identity.
- Select the independent runner/account/administrator and prove the Windows administrator has no management or secret access.
- Define how the runner obtains the direct credential without exposing it to Windows and how that credential is revoked after one attempt.
- Select a free, already-owned, self-hosted or paid authority only after documented cost review and explicit approval.
- Define exact trusted time source/skew policy for manifest validity; monotonic time only applies after process start.
- Define incident process if signer, authority, Neon metadata, or release identity disagree.
- Independently verify actual endpoint/project metadata, PostgreSQL 17 and role/grant readiness.
- Qualify existing 1s/5s/10s migration bounds on a separately authorized disposable branch.
- A local administrator can still run arbitrary local binaries and fabricate local evidence; those outputs are explicitly non-authoritative. The architecture fails if the administrator obtains the runner, signer, authority or direct-credential control plane.

## 16. Local-only suitability decision

**A local-only solution cannot meet the required threat model.**

It can protect against accidental reuse, ordinary unprivileged file replacement and process crashes on an intact host. It cannot provide trustworthy one-use authorization across administrator compromise, local ledger deletion, environment/path substitution, or host loss. Meeting those requirements needs:

- An independently controlled signing key with pinned public verification key; and
- An independently controlled append-only attempt authority whose migration principal cannot delete/reset history.
- An independently administered migration runner and credential broker that do not release the direct operator credential to the compromised Windows host.

Until both are selected, implemented and adversarially tested, A4 migration execution remains blocked.
