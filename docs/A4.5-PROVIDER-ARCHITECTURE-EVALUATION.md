# A4.5 — Independent Security Infrastructure Provider Evaluation

**RESEARCH AND DESIGN ONLY — NO-GO FOR IMPLEMENTATION OR MIGRATION.** This evaluation was researched on **2026-11-04**. It authorizes no provider login, account change, provisioning, deployment, secret creation, Neon connection, SQL, migration, Git operation, or production activation. Provider documentation describes capabilities, not this project's configured state; no account or service was inspected.

## 1. Executive summary

### 1.1 Decision

**NO-GO: no end-to-end, genuinely zero-spend architecture has been verified to satisfy A4.4 and remain safe after compromise of any one supporting security-infrastructure account.** A4 migration execution remains blocked.

Several free components are useful but insufficient alone:

- GitHub-hosted standard runners are independent of the Windows host and free for public repositories. GitHub Free also includes $12/month of private-repository compute and 500 MB of artifact storage, but Free required reviewers and environment secrets are public-repository-only.
- Cloudflare Durable Objects on Workers Free provide transactional, strongly consistent SQLite storage and ample limits for rare A4 attempts. They provide atomic compare-and-set semantics, not account-administrator-resistant immutability: Worker code can call `deleteAll()`, SQLite storage has 30-day point-in-time restore, and an account administrator able to replace Worker code can change the authority.
- Sigstore Rekor provides an append-only, publicly auditable transparency log. It proves publication and supports detection; it does not atomically reserve a project-specific one-use migration attempt or decide whether a credential may be released.
- An independently administered Linux host can move execution and credentials away from Windows, but one host containing runner, ledger, signer, and credential is one compromise domain. Ordinary files, Git, PostgreSQL, SQLite, backups, or a self-hosted Rekor instance administered by that host are not immutable against that administrator.
- Managed KMS and WORM services improve key custody and evidence retention but are not zero-cost in the evaluated configurations and do not by themselves prevent a compromised cloud account from using its own broker or database credential.

The **conditional target architecture** is a cross-provider, two-broker design:

1. an offline or hardware-backed, independently administered metadata/approval signer;
2. an exact-release GitHub-hosted ephemeral runner with no GitHub-stored Neon secret;
3. a Cloudflare Durable Object used as one transactional coordinator, not the sole authority;
4. two independently administered credential-share brokers on different providers, each with its own create-if-absent/consumed-attempt record;
5. 2-of-2 split custody of the direct Neon migration credential, so no provider holds the usable credential;
6. signed receipt digests published to Rekor and retained in at least one WORM-capable store for audit evidence.

That target can be designed to tolerate compromise of one **supporting** account because an uncompromised broker and coordinator still block replay, and one stolen credential share is unusable. It is not deployment-qualified: the broker implementations, administration, credential rotation, Neon role, release packaging, cost ceiling, and recovery procedures are unresolved and untested. Compromise of the Neon control-plane account remains outside A4.4; if scenario 10 is intended to include that account, this design is also a NO-GO because a Neon project administrator can independently reset privileged role passwords or alter the target.

“Independent account” means more than a different username. It requires a different authorized custodian and recovery path, hardware-backed MFA, no session/API token/password manager/recovery email on the Windows host, no common administrator who can reset both domains, and separately reviewed billing and organization-owner access. GitHub and Cloudflare accounts controlled by the same person, IdP, recovery mailbox, browser profile, or compromised Windows password manager are **not** independent.

## 2. Required security result

The authoritative runner must independently fetch and verify the exact signed manifest and release, reserve one attempt, receive signed `MIGRATION_STARTED` receipts, obtain a direct Neon capability without exposing it to Windows, run only the existing migration runner, and preserve an external blocking state after crash or lost COMMIT response. Windows may request and display results only.

This evaluation adds the requested scenario-10 criterion to A4.4 as follows:

- Compromise of any one supporting account (GitHub, Cloudflare, or one credential-broker cloud) must not permit an altered release, forged approval, usable Neon credential, replay, ledger reset that enables retry, or deletion of every authoritative receipt.
- A simultaneous compromise of two independent supporting domains is outside this added criterion.
- Provider-platform compromise and Neon provider/control-account compromise remain outside A4.4 section 2.3. Expanding scope to either requires a new threat-model decision.

## 5. Candidate A — GitHub-hosted Actions, Cloudflare DO, independent signer/broker

### 5.1 Verified capabilities

- Standard GitHub-hosted jobs use newly provisioned VMs for the normal Linux runner classes; GitHub's security guidance describes GitHub-hosted runners as ephemeral and clean isolated VMs. This moves execution outside Windows.
- GitHub OIDC includes `repository_id`, `repository_owner_id`, `workflow_sha`, `workflow_ref`, `run_id`, `run_attempt`, `environment`, `event_name`, and whether the runner is GitHub-hosted. Reusable workflows also expose `job_workflow_sha`. Repositories created after 2026-07-15 use immutable IDs in the default subject; older repositories must opt in. An external broker can validate immutable IDs and exact workflow SHA rather than branch names.
- GitHub recommends workflow dependency lockfiles or full-length commit-SHA pinning. Exact action pins reduce tag-movement risk but do not make a repository administrator an independent approver.
- GitHub environments can require reviewers, prevent self-review, restrict deployment branches, and disallow administrator bypass. On GitHub Free/Pro/Team, required reviewers, wait timers, custom protection rules, and environment secrets are available only for public repositories.
- Cloudflare SQLite-backed Durable Object storage is transactional and strongly consistent. Storage methods are implicitly transactional; explicit transactions and single-object serialization can implement create-if-absent and compare-and-append.
- Cloudflare Free includes 100,000 Durable Object requests/day, 13,000 GB-s/day, 5 million row reads/day, 100,000 row writes/day, and 5 GB total SQLite storage. This is far above a rare A4 qualification attempt.

### 5.2 Mandatory-criteria assessment

| Criterion | Assessment |
| --- | --- |
| Administrative separation | **Assumption until proven.** Different GitHub and Cloudflare account names are not enough. Named owners, recovery paths, MFA, sessions, tokens, IdP, and Windows exclusion must be evidenced. |
| Protected release/workflow | **Conditional.** Broker must reject every OIDC token except exact immutable repository/owner IDs, exact `workflow_sha`, GitHub-hosted runner, approved event/environment, manifest/release hash, run ID and attempt. No mutable tag, branch, downloaded script, package install, or unpinned action may enter the privileged job. |
| Signing custody | **Unresolved.** The signer must be offline/hardware-backed and outside both accounts. GitHub keyless signing alone inherits GitHub-account/IdP compromise and is transparency evidence, not independent approval. |
| Atomic one-use | **Meets honest-service semantics.** A DO can serialize and transactionally reject duplicate `(manifestId, sequence, releaseHash)` reservations. |
| Append-only/deletion resistance | **Fails as sole authority.** The storage API supports deletes and atomic `deleteAll()`; PITR restores the database to an earlier point within 30 days. An account administrator able to deploy new Worker code can invoke those capabilities or replace transition logic. PITR is recovery, not WORM. |
| Independent manual approval | **Must be external.** GitHub required reviewers are useful defense in depth but repository/environment administrators are in the GitHub domain, and Free private repositories lack the feature. |
| Execution outside Windows | **Verified capability.** Use a standard GitHub-hosted VM, not the compromised host and not an unqualified self-hosted runner. |
| Neon credential isolation/revocation | **Unresolved.** The direct credential must not be a GitHub secret or artifact. A separate broker must release it only to the exact job. Native short-lived Neon PostgreSQL credentials were not established. |
| Recovery | DO idempotency can reconcile lost reserve/start responses. After `MIGRATION_STARTED`, runner crash or lost COMMIT response remains unknown and blocks retry. Cloudflare account-level reset remains fatal without another consumed-attempt authority. |
| Limits/billing | DO can fit Free. Public standard GitHub runners are free; private GitHub Free includes $12 compute and 500 MB artifacts. With no valid payment method, GitHub blocks usage after included compute. Avoid artifacts containing manifests with sensitive metadata. |
| Repository visibility | Public is required to use GitHub Free required reviewers/environment secrets and gives free standard compute. A private repository can use included compute only if approval and secrets are entirely external; therefore public visibility is not a security requirement of the external-gate design. |
| Windows-admin resistance | **Yes only if all accounts, signer, broker, and release source are truly inaccessible from Windows.** |

### 5.3 Decision

**NO-GO.** Cloudflare DO is acceptable as a transactional coordinator, but not as the sole non-resettable attempt authority. A single broker holding the usable Neon credential is also a single bypass domain. Rekor anchoring can expose a reset later; it cannot stop a reset ledger from authorizing a second attempt now.

## 6. Candidate B — independently administered Linux runner stack

This candidate uses a dedicated Linux host for the orchestrator, an independent signer, and a separate append-only attempt service. It does not require GitHub or a public repository.

| Criterion | Assessment |
| --- | --- |
| Administrative separation | Can satisfy A4.4 only if the host, hypervisor, network management, backups, SSH keys, console, recovery media, and signer are unavailable to the Windows administrator and controlled by another custodian. A VM/container on the Windows host fails. |
| Release/workflow integrity | Requires an offline-signed release manifest, reproducible/package hash verification, pinned runtime, no package installation at execution, read-only image, and a second authenticated release source. Files owned by the Linux root administrator are not immutable against that administrator. |
| Signing custody | An offline Ed25519 key or hardware token controlled by a different approver can qualify. A key file or token PIN stored on the runner cannot. |
| Atomic one-use | A separate transactional service can implement it. SQLite/PostgreSQL on the runner cannot serve as an independent authority against runner-root compromise. |
| Append-only/deletion resistance | Needs WORM media/service or multiple independently administered witnesses. Filesystem append flags, backups, signed Git commits, and ordinary database WAL are administrator-resettable. |
| Independent approval | A second human/hardware signer can qualify. An SSH login by the runner administrator alone cannot. |
| Execution outside Windows | Yes. GitHub documents that self-hosted runners cost no GitHub Actions fee, but the operator is responsible for the machine and self-hosted runners do not inherently start clean for every job. A direct systemd/one-shot runner is simpler than attaching this sensitive host to untrusted CI. |
| Credential isolation/revocation | A broker on another host/domain is still required. If the runner administrator can query the full credential at will, that administrator is a migration authority. |
| Recovery | A remote authority must survive runner loss. Any post-start crash is unknown; a clean replacement runner may perform read-only inspection only. |
| Limits/billing | Software can be open source, but hardware, hardware token, power, secure backup, network, patching, monitoring, and independent operator time are costs. A claim of $0 is valid only if all suitable resources already exist and are explicitly contributed. |
| Repository visibility | No public repository required. |
| Windows-admin resistance | Yes if physically/logically separate; no if managed, recoverable, or reachable through credentials on Windows. |

**Decision: NO-GO as currently unspecified.** This is a viable architecture class, not a selected architecture. A single “independent Linux box” that combines runner, signer, authority, broker, and backups fails one-domain compromise and deletion resistance. It becomes qualifying only by adding at least a separate signer and separate one-use/credential authority, which removes the claimed simplicity and requires named hardware and administrators.

## 7. Candidate C — managed KMS/HSM, hosted runner, durable authority

Representative evaluated services are AWS KMS/S3 Object Lock/Secrets Manager, Google Cloud KMS/Secret Manager, Azure Key Vault/Managed HSM, and a GitHub-hosted runner.

### 7.1 Verified capabilities and costs

- AWS KMS customer-managed keys cost **$1/key/month**, prorated. The 20,000-request free tier excludes asymmetric `Sign`, `Verify`, `Encrypt`, `Decrypt`, and `GetPublicKey` requests. KMS key policies are the primary access control.
- AWS Secrets Manager charges **$0.40/secret/month** plus API operations; time-limited new-account credits are not a permanent free tier.
- S3 Object Lock compliance mode prevents overwrite/deletion of a protected object version by any user, including account root, until retention expires. It is useful WORM evidence. It does not prevent creation of a conflicting new version, choose the authoritative state, or perform atomic attempt reservation. Deleting the AWS account is documented as the only early deletion route for compliance-locked data.
- Google Cloud KMS requires billing. Software-protected active key versions are approximately **$0.06/month**; Autokey has free limits of 100 active versions and 10,000 cryptographic operations, but Autokey suitability for this exact signing/broker design is unverified. HSM key versions are paid. Google Secret Manager includes six active versions and 10,000 accesses/month, with billing beyond those limits.
- Azure Key Vault and Managed HSM are metered paid services. The official dynamic pricing page did not expose stable numeric values in this research response, so no exact Azure estimate is asserted.
- Cosign officially supports AWS KMS, GCP KMS, Azure Key Vault, HashiCorp Vault, and OpenBao, but support for a key URI does not establish correct administration or one-use authorization.

### 7.2 Security assessment

| Criterion | Assessment |
| --- | --- |
| Administrative separation | Strong IAM is possible, but two services inside one root cloud account are not independent from account takeover or owner recovery. |
| Release/workflow integrity | Hosted-runner OIDC and KMS policy can bind exact repository/workflow claims. AWS does not support GitHub custom OIDC claims in the same way as all providers, so the broker itself should validate the full token before any release rather than assuming an IAM trust policy covers every claim. |
| Signing custody | Managed KMS prevents private-key export and logs operations. A cloud account able to change policy or invoke signing is still the signer domain. HSM protects key material, not approval policy from an authorized account administrator. |
| Atomic one-use | DynamoDB/Firestore or another transactional store can implement conditional create. This requires a concrete schema, consistency proof, idempotency design, and policy review. |
| Append-only/deletion resistance | S3 Object Lock compliance gives strong retained evidence. It cannot by itself prevent an attacker from creating a false current state or using a stolen full DB credential. CAS plus WORM is required. |
| Independent approval | Must be held outside the KMS/broker account or use true threshold/multi-domain approval. A button in the same compromised cloud account is not independent. |
| Execution outside Windows | GitHub-hosted or another managed ephemeral runner qualifies. |
| Credential isolation/revocation | A managed secret protects at rest but returns plaintext to an authorized broker. If one cloud account stores the full Neon credential, its compromise bypasses every ledger. |
| Recovery | Managed durability and WORM improve recovery. Unknown database outcomes still require independent read-only inspection and no retry. |
| Limits/billing | Requires billing/payment relationships in the evaluated KMS clouds. HSM has materially higher costs. Budgets are alerts/limits, not proof of zero spend unless provider hard-stop behavior is verified. |
| Repository visibility | Private is possible with external approval and available hosted-runner allowance. |
| Windows-admin resistance | Yes if no account/recovery/credential is reachable from Windows. |

**Decision: NO-GO for a single-cloud design.** It is stronger operationally than DO alone but fails scenario 10: compromise of the account containing KMS/broker/full Neon secret permits direct credential use even if WORM receipts later reveal the abuse. Managed storage does not turn a bearer database password into a threshold capability.

## 8. Candidate D — simpler offline signer, hosted runner, and Rekor

The simplest plausible design signs the manifest/release offline, runs the exact job on GitHub, and writes receipts to public Rekor or a signed Git log.

- **What it solves:** Windows cannot forge the signer; exact release hashes detect local replacement; GitHub-hosted execution is outside Windows; Rekor makes signed receipt publication discoverable and append-only under monitored operation.
- **What it does not solve:** Rekor has no project-specific atomic create-if-absent reservation, expected-state transition, private credential release policy, or retry lock. A manual paper/Git ledger has no network-atomic exclusion across concurrent jobs. A signed log can contain two conflicting, validly signed attempts.
- **Account risk:** Sigstore's threat model states that OIDC account or provider compromise can produce unauthorized certificates; monitoring detects misuse but does not prevent it. A self-managed offline key avoids that IdP dependency, but the singular credential custodian remains a bypass.

**Decision: REJECTED.** Transparency is evidence, not authorization. This candidate fails repeated-run, atomic reservation, credential-broker, and one-provider-compromise requirements.

## 9. Candidate E — conditional cross-provider target

### 9.1 Components and roles

| Domain | Required role | Must not hold/control |
| --- | --- | --- |
| Offline/hardware signer | Sign canonical metadata and a short-lived human approval over manifest hash, release hash, attempt nonce, purpose and expiry | Neon credential, broker admin, runner admin |
| GitHub | Run exact immutable workflow on ephemeral hosted VM; issue OIDC identity | Neon secret, signer key, authority reset credential |
| Cloudflare DO | Serialize one reservation/state chain and return signed/domain-authenticated receipts | Sole authority, full Neon credential, signer key |
| Broker A (for example AWS) | Validate all bindings; atomically mark attempt consumed; release share A only after start policy | Share B, full Neon credential, GitHub/Cloudflare administration |
| Broker B (different provider, for example GCP) | Same independently for share B | Share A, full Neon credential, GitHub/Cloudflare administration |
| Rekor/WORM stores | Retain receipt/manifest digests for public or compliance evidence | Authorization decisions or credentials |
| Neon | Host only the approved disposable branch and branch-scoped least-privilege roles | Attempt history or supporting-provider recovery credentials |

### 9.2 Why two brokers are necessary

Each broker stores only one 2-of-2 share and an independent consumed-attempt record. A compromised broker account obtains at most one unusable share and cannot make the honest broker release its share for an unsigned, expired, mismatched, modified-workflow, or consumed attempt. A reset Cloudflare ledger does not reset either broker ledger. A compromised GitHub administrator can launch or modify workflows, but modified `workflow_sha`/release hashes fail external checks and the exact workflow remains constrained by the signed manifest and one-use records.

This is prevention, not merely detection. Rekor and WORM copies remain necessary for audit/recovery, but neither substitutes for the honest broker's refusal.

### 9.3 Conditions before this could qualify

1. The two broker products and conditional-write stores must be selected, documented, and tested for linearizable create-if-absent and idempotent read-after-lost-response behavior.
2. Broker trust must validate the JWT signature/issuer/audience/time and exact immutable owner/repository IDs, `workflow_sha`, event, environment, `runner_environment=github-hosted`, run ID and attempt. The current repository's immutable-subject opt-in status is unknown.
3. The release must be a signed, dependency-complete artifact/container by digest. No `npm install`, mutable action/tag, branch checkout, caller-controlled reusable workflow, or network-downloaded executable may enter the privileged phase.
4. Broker A, Broker B, Cloudflare, GitHub, signer, and Neon administrators/recovery channels must be enumerated. Shared custodians that collapse the assumed independence must be rejected.
5. Share generation, storage, release, in-memory reconstruction, zeroization, post-attempt rotation, crash handling, and revocation must pass adversarial review. “Encrypted in two clouds” is not proof of 2-of-2 custody.
6. At least two independent consumed-attempt records must remain authoritative. A public Rekor monitor and retained signed receipts must detect inconsistent history.
7. A separate read-only preflight/inspector capability must not unlock migration. Migration shares are released only after all required signed `MIGRATION_STARTED` transitions.
8. Billing must have explicit hard stops or approved maximum spend. No trial credit counts as permanent free feasibility.

### 9.4 Decision

**Conditionally recommended as the target for a future design/prototype; not approved for provisioning.** It is the minimum evaluated pattern that can credibly tolerate one supporting-account compromise. It is not simple, not currently verified free, and not yet implementable safely.

## 10. Credential lifecycle

### 10.1 Provisioning

1. Under a future, separate database-access approval, create a SQL-defined, branch-scoped migration login with only the DDL/ownership capabilities required by the two approved migrations on the disposable branch. Neon documents that Console/API/CLI-created roles inherit `neon_superuser`; those methods are therefore unsuitable for the least-privilege migration role.
2. Create a separate read-only preflight/inspector role. It must not own schema objects, create schema, alter roles, or run migrations.
3. Generate a high-entropy migration password in an approved independent environment, split it 2-of-2 before storage, and deliver one share to each broker. The unsplit value must never traverse Windows, GitHub secrets, repository variables, artifacts, logs, command arguments, chat, or either provider's administrator interface.
4. Destroy any provisioning copy only after both brokers prove storage and the Neon role is verified under a separately approved test. No such operation is authorized by A4.5.

### 10.2 Per-attempt release

- The read-only credential may be separately brokered for preflight after `RESERVED`; it cannot be promoted into the migration credential.
- Each migration broker independently verifies signer approval, exact manifest/release, expiration, DO reservation, its own unused record, and exact hosted-runner OIDC claims.
- Each broker atomically changes its local state to `MIGRATION_STARTED/CONSUMED` before returning its share. Lost broker response is not retried as a new release; it is reconciled by attempt/run/idempotency key.
- The runner reconstructs the direct connection capability only in private process memory after it holds every required start receipt. It masks values, omits them from environment/arguments and artifacts, opens one bounded direct connection, and destroys the process after use.

### 10.3 Rotation and revocation

- Neon documents that password reset takes effect immediately for the next connection and is branch-scoped. That is a usable revocation mechanism, but API/Console management of such roles may imply `neon_superuser` and a high-value Neon control credential.
- No documented native, automatically expiring Neon PostgreSQL credential suitable for this migration was verified. Therefore short-lived credential issuance is a **blocker**, not an assumed feature.
- On success, the credential should be rotated and newly split before any future attempt. On crash/unknown outcome, both broker records remain consumed and the old shares are never released again. An independently approved database custodian must inspect and rotate/revoke before a new manifest; no automatic recovery may reuse the credential.
- If one broker is compromised, revoke that broker's share and management identity, rotate the Neon password through a separately approved path, create entirely new shares, and issue a new signer sequence. Do not reconstruct using the surviving old share.

## 11. Attempt reservation and recovery protocol

### 11.1 Protocol

1. **Prepare:** signer independently validates target metadata and signs the canonical A4.4 manifest. A separate approval signature binds manifest hash, exact release hash, purpose, random attempt nonce, trusted expiry, and the proposed GitHub workflow SHA.
2. **Identify job:** exact hosted workflow obtains a GitHub OIDC token. All authorities verify immutable repository/owner IDs and exact claims; no Windows assertion is trusted.
3. **Reserve coordinator:** DO performs atomic create-if-absent for `(manifestId, sequence, releaseHash, signatureHash)`. Duplicate calls return the same attempt/status.
4. **Reserve brokers:** A and B each atomically create the same attempt as `RESERVED`. If one reports an existing conflicting/started/closed record, stop. Lost responses are read back by idempotency key.
5. **Preflight:** broker a separately restricted read-only capability; run A4.4 preflight. Destroy the child/socket. Append `PREFLIGHT_PASSED` to all reachable authorities and publish signed digest evidence.
6. **Start:** consume the local monotonic approval. Obtain compare-and-append `MIGRATION_STARTED` receipts from DO, broker A, and broker B. Any partial/lost result is reconciled; if all signed acknowledgments cannot be proven, no migration process starts and the attempt is blocked/unknown.
7. **Release:** after each broker has durably marked its own record consumed, it releases only its share to the exact run/attempt. The runner reconstructs the credential in memory only after verifying every start receipt.
8. **Execute once:** run only the approved migration/checksums/catalog verification. No wrapper retry is permitted.
9. **Finalize:** append `QUALIFIED` only after post-commit verification and credential cleanup. Any timeout, process death, cleanup problem, append failure, or lost database response after start appends or is conservatively treated as `OUTCOME_UNKNOWN`.
10. **Anchor:** publish only non-secret hashes/signed receipts to Rekor and retained WORM copies. Failure to anchor after start is an incident but never permission to rerun.

### 11.2 Recovery rules

| Event | Required result |
| --- | --- |
| Crash before any start transition | Reservation remains. Human may close only after proving no migration credential was released. No reuse of the old attempt. |
| One authority records start and another response is lost | Query all by idempotency key. Until all required signed start receipts are proven, do not run migration; classify blocked/unknown. |
| Runner crashes after start | Brokers remain consumed; DO remains started; run a separately authorized read-only inspector. Never rerun automatically. |
| Neon commits but runner loses response | `OUTCOME_UNKNOWN`; independent inspection classifies exact committed, fully absent, or partial/mismatch. |
| Credential broker unavailable before start | Stop with reservation retained. Unavailability never downgrades to a local/GitHub secret. |
| Credential broker unavailable after another authority starts | Treat as blocked/unknown. Do not replace the broker or reconstruct from backups during the attempt. |
| GitHub host/run is lost | A replacement run cannot obtain consumed shares. It may perform signed read-only inspection only after separate approval. |
| Local Windows receipts are all deleted | No effect on DO/brokers/WORM/Rekor; deletion is an incident. |
| One supporting account is compromised | Freeze new attempts, rely on the remaining independent records, revoke/rotate the affected identity/share, and require a new sequence after incident review. |

### 12.1 Scenario-specific conclusions

1. **Manifest replacement:** only an independently obtained, pinned signer key and exact canonical signature are authoritative. A signature check performed only on Windows is irrelevant.
2. **Release replacement:** Git commit/branch names are insufficient. The approval and broker policy bind the exact workflow and release hashes; the runner fetches from an independently authenticated source.
3. **Receipt deletion:** no local receipt grants permission. At least two remote consumed records plus audit witnesses survive.
4. **Repeated runs:** GitHub concurrency controls are defense in depth. Provider-independent CAS/consumed state is the security control.
5. **Repository-admin workflow change:** repository rules and CODEOWNERS help, but the decisive control is external rejection of a new `workflow_sha`. Repository administrators must not administer that policy.
6. **Cloudflare reset:** DO/PITR is not WORM. Candidate E remains blocked by both broker records; candidates relying on DO alone fail.
7. **Post-start crash:** always unknown, never a reason to rerun.
8. **Lost COMMIT response:** database inspection, not transport inference, determines disposition. The old attempt remains consumed even if inspection finds absence.
9. **Broker outage:** fail closed. Copying the credential into GitHub/Windows “for availability” destroys the trust boundary.
10. **One account compromised:** audit evidence alone is insufficient. Candidate E requires that no one account has both a usable credential and authority to make the other domains release/forget it.
